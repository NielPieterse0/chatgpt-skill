# Writing Style

Use clear, direct prose based on the Google Developer Documentation Style Guide. This skill shapes presentation; it does not replace task-specific authority, technical methods, or factual verification.

Project-specific instructions and explicit user requirements take precedence. Preserve exact identifiers, commands, code, quoted text, required terminology, and formal wording when accuracy or authority depends on them.

## Default writing rules

- Put the decision, result, action, or other critical information first.
- Use plain English and specific nouns and verbs. Prefer familiar words over jargon, buzzwords, or vague abstractions.
- Use active voice when it makes the actor clearer.
- Address the reader as `you` when direct instruction is appropriate; avoid unnecessary `we` language.
- Put conditions, circumstances, or goals before the instruction they qualify.
- Keep sentences focused. Keep each paragraph to one main idea and make paragraphs easy to scan.
- Use a conversational, respectful, professional tone without slang, cutesiness, hype, or forced humor.
- Avoid filler and empty framing such as `please note`, `at this time`, `simply`, `obviously`, `easy`, or similar claims about difficulty.
- Avoid excessive claims. State uncertainty, limitations, missing evidence, and incomplete work explicitly.
- Use sentence case for headings unless project style requires otherwise.
- Use numbered lists for ordered procedures and bullets for non-sequential items when a list improves scanning.
- Use descriptive link text and accessible, inclusive language suitable for a global audience.

## Progressive style lookup

Do not load a complete style-guide corpus for routine writing. When a detailed style question matters:

1. Start from the style-guide index provided by the current project.
2. Identify the narrow topic involved in the current output.
3. Read only the relevant page or pages.
4. Apply project-specific style first, then the detailed guide where the project is silent.

Typical lookups include tone and voice, sentence or paragraph structure, terminology, headings and lists, procedures, accessibility and inclusive language, punctuation, code formatting, UI elements, dates, and links. Use a word list only for an actual terminology or spelling question.

If the detailed guide is unavailable, apply the default rules above rather than inventing a rule from memory.

## Apply with other workflows

Use this skill as a presentation layer. A planning, coding, documentation, review, security, or operations skill still owns the underlying task. Do not change technical conclusions, scope, evidence, severity, or required structure merely to make prose smoother.

For user-supplied writing, preserve the requested voice and format unless the user asks for style normalization. For templates, schemas, generated data, legal text, or other controlled language, change only prose that is actually editable.

## Final pass

Before sending or committing human-facing prose, check that:

- the important information appears before background detail;
- each sentence has a clear purpose and actor where one matters;
- conditions precede the instructions they control;
- paragraphs and lists are short enough to scan;
- jargon, filler, repetition, hype, and unsupported certainty are removed;
- headings, links, code terms, identifiers, and UI labels are formatted consistently;
- the output remains accurate to its source evidence and higher authority.

Stop editing when further stylistic change would not improve clarity, correctness, accessibility, or decision usefulness.
